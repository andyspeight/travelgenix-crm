## Phase 6 — the Attio review, revisited (in progress)

Andy shared attio.com as the fastest-growing CRM in the general B2B space and
asked what we could learn. Most of their playbook we were already running —
AI in the data model rather than a bolted-on chatbot, a conversational layer,
and reporting that is a documented weakness of theirs and a strength of ours.
Three places they were genuinely ahead:

1. **Sequences** — multi-step, stop-on-reply. ← DONE
2. **Enrichment on create** — theirs is company/LinkedIn data; the travel
   version is school-holiday flags, visa and passport-validity rules, flight
   times, seasonality.
3. **Reply and engagement tracking** — inbound email onto the timeline, opens
   and replies, not just sends.

- [x] **1. Sequences** (31 Jul) — a chase that runs over days and stops the moment it should.
  - **Schema**: `sequences` / `sequence_steps` / `sequence_enrolments` (applied live, RLS policies included from the start). `delay_days` is measured from ENROLMENT, not from the previous step, so editing one step cannot silently shift everything after it. A unique index means nobody is ever chased twice down the same track for the same thing.
  - **`lib/sequences/engine.ts` (14 tests)** — the decision, and the care is all in stopping. Every stop condition is checked BEFORE considering a send, on every evaluation, not only when a step is due: a reply on day 2 must stop the chase before day 3 comes round. Stop reasons, in priority order: an agent pressed stop, they replied, the thing resolved (quote accepted/declined/answered), the address is undeliverable, marketing consent withdrawn. Consent is consulted for MARKETING sequences only — chasing a live quote is service under PECR, and stopping it on a marketing withdrawal would abandon someone mid-booking. Plus: never two steps in one day even if a run was missed, so catching up cannot arrive as a burst.
  - **`lib/email/send.ts`** — the send pipeline lifted out of its HTTP route so an unattended sequence send passes exactly the same consent check, suppression check and per-agency sender identity as a human-pressed one. The route is now a thin wrapper; there is one pipeline, not two.
  - **`lib/sequences/runner.ts`** — enrols via the existing journeys matcher (one trigger vocabulary, not two), then evaluates every active enrolment. A provider refusal stops the whole chase and records the provider's own words, rather than retrying nightly.
  - **Safety**: `auto_send` is per sequence and defaults FALSE. In review mode each step becomes a task in the queue agents already work, with the wording ready. The starter installs PAUSED and in review mode — nobody should discover their CRM chasing customers with words they have never read.
  - **UI**: `/sequences` — the steps as chips, live counts, and a "Stopped — and why" list, which is the bit that tells an agent the automation is behaving itself. Sidebar, palette and tour entries.
  - **Cron**: sequences run in the same nightly pass as journeys.
- [x] **2. Enrichment on enquiry** (1 Aug) — the travel-native answer to Attio's auto-enrichment. They fill in company size and LinkedIn; none of that matters for a family booking Crete. What matters is the two things an agent looks up by hand and occasionally gets wrong expensively:
  - **School holidays** — do the dates fall in an English school holiday? That sets the price band before anyone quotes. With children: expect peak pricing, and check whether either end can shift. Without children: they could save real money by moving a few days. Term time with children: raise the school authorisation before they get attached to the price.
  - **Passport validity** — Schengen (3 months beyond departure) and the common six-month rule for long-haul, checked against each traveller's expiry. Expires before they get home / margin under the requirement, each flagged with the rule quoted.
  - **Lead time** — a departure inside six weeks, because a passport problem found next week is a problem found too late.
  - **`lib/enrich/enquiry.ts` + `reference.ts` (15 tests)**. Three deliberate restraints: **this is never advice** — every fact quotes the rule it applied and points at what to check, because "check this, here's why" is useful and "you're fine" from software that was wrong is a disaster. **Silence beats a guess** — outside the reference table's covered years, or for a destination we hold no rule for, it says nothing rather than implying term time or safety. And it **admits what it does not know**: we hold passport expiry but not issue date, so the EU 10-year rule is raised as a question rather than quietly skipped.
  - Reference data is isolated in one file with an explicit validity window, because it is the part that goes stale.
  - Rendered on each enquiry card, warnings first, each with its source.
- [x] **3. Reply and engagement tracking** (1 Aug) — the other half of the conversation. Until now the CRM knew what it *sent*; a customer answering was invisible, so the enquiry still read "waiting", the chase carried on, and the only thing that stopped either was an agent noticing in their own inbox.
  - **`lib/email/inbound.ts` (19 tests)** — parse, strip the quoted original, and tie the reply back to a send. Correlation, strongest first: **the reply address** (`reply+<sendId>@<inbound domain>`, exact, no header archaeology), **the thread headers** (In-Reply-To / References against the provider message id — a bonus when it works, never the foundation), **the sender's address** (one contact = almost certainly them), then **nothing** — said plainly and parked, because a customer's reply disappearing quietly is the worst outcome available. An address that exists in two agencies is refused rather than guessed at.
  - **An out-of-office is not a reply.** Detected on `Auto-Submitted` / `X-Autoreply` / `Precedence` and the subject line, recorded on the timeline flagged as automatic, and excluded from the reply signal. Stopping a chase on an out-of-office would be exactly backwards: the one person we *know* has not read the email would be the one we stop chasing.
  - **`app/api/email/inbound/route.ts`** — SendGrid Inbound Parse, token-authenticated like the bounce webhook, always answering 200 (a 500 makes the mail server bounce the customer's reply back at them). A unique index on the RFC message id makes a retry harmless. The chase stops by *itself*: the runner already treats an inbound interaction as "they replied", so writing the timeline entry is the whole mechanism — no second path that could disagree.
  - **`lib/email/engagement.ts` (13 tests)** — delivered / opened / clicked, folded onto the send row from the same shared webhook. The wording is the design: **an open is not proof anyone read it** (Apple Mail Privacy Protection and corporate scanners fetch the pixel unprompted), so it is labelled a hint with the caveat attached; a click is labelled as evidence of a person; a reply outranks both. **Engagement never stops a sequence** — chasing someone who opened but did not answer is precisely what a chase is for.
  - **`email_inbound`** records every reply we accept, matched or not, with the match reason stored rather than inferred, so confidence stays visible.
  - **Health check** — "Replies coming back", the quietest failure in the product: inbound misconfigured means customers *are* answering and the CRM shows nothing. It says plainly when replies are going somewhere else, and counts the unfiled ones.
  - **Hardening**: the forgotten-filter check was being fooled by `agency_id` appearing in a `select()` column list rather than in a filter. It now blanks select arguments before looking, with a test that proves it.
  - **ACTION FOR ANDY (optional, when you want replies in the CRM)**: in SendGrid, set up **Inbound Parse** on a subdomain you own — e.g. `reply.crm.travelify.io` — with the destination URL `https://crm.travelify.io/api/email/inbound?token=<EMAIL_WEBHOOK_SECRET>`, add the MX record it gives you, then set `EMAIL_INBOUND_DOMAIN=reply.crm.travelify.io` in Vercel. Until that is set, everything else still works — the CRM just won't see replies, and Settings says so in those words rather than staying quiet. Note the rule: an agency that has set its **own** reply-to address keeps it, and their replies go to their own inbox, not into the CRM.

## Phase 7 — the composer (in progress)

- [x] **A proper email composer** (1 Aug) — formatting, attachments, spellcheck, emoji and an AI rewrite pass, in one component used everywhere the CRM sends. It replaces two separate plain textareas that had drifted apart.
  - **Formatting without an HTML sanitiser.** The browser never sends HTML. The composer converts what the agent typed into a small strict document (paragraphs, headings, lists, quotes; bold / italic / underline / link) and the SERVER renders the email from that. There is no sanitiser to get wrong because there is no HTML to sanitise, and a whitelist you build the output from cannot leak what it cannot express. `lib/email/rich-text.ts` + `rich-text-dom.ts`, 22 tests including pasted scripts, `javascript:` links and supplier price tables.
  - **What you see is what they get.** After a paste the editor is rebuilt from the document we would actually send, so a pasted image or styling that cannot survive the send does not survive the paste either. No agent looks at a formatted table on screen and finds the customer got a wall of text.
  - **Every email carries a plain-text half**, built from the same document, so the two can never say different things — and a message with no text part looks like spam to filters.
  - **Attachments** (`lib/email/attachments.ts`, 15 tests) — private bucket, per-agency prefix, no public URL at any point. Filenames are rewritten, content types are derived from the extension rather than believed, and the size is measured from the bytes that arrived rather than what the browser claimed. Executables are refused with the real reason: a program arriving from a travel agent is what a scam looks like. 5MB a file, 10MB an email, 5 files.
  - **Spellcheck is the browser's, in British English.** Instant, offline, already knows the agent's own dictionary, and the contents of a customer's email are not sent to a third party to be checked for typos.
  - **Improve writing** (`lib/email/improve.ts`, 16 tests + `/api/email/improve`) — the most dangerous button in a CRM, so it edits and never authors. Five modes (polish, spelling & grammar, shorter, warmer, more formal). The prompt forbids adding facts; then the response is CHECKED deterministically — every number, date, link and address in the rewrite is compared with the draft, anything new is named in plain English, and a rewrite that invented something cannot be applied with one click at all. Facts the rewrite quietly dropped are surfaced too. Em dashes are repaired rather than reported; marketing words the agent did not write are flagged.

  - **Nothing is stored.** Every attribute is computed on read from the rows as they are right now. That is the deliberate difference from an AI-filled field: a value written into a record is true the day it is written and drifts quietly for ever after — the passport gets renewed, the customer books, and the field still says what it said in March. A derived attribute cannot go stale and cannot be edited into something the data does not support.
  - **Every attribute carries its reason**, built from the real values. "Passport risk" on its own is an accusation; "Sam's expires 1 Dec 2026, under the six months most countries ask for" is a fact an agent can act on or dismiss.
  - **Missing data is its own attribute, not a risk.** A customer with no passport date is "passport not on file", a different problem with a different fix — never silently counted as safe or as at-risk.
  - **On /customers**: a "What Luna worked out" chip row with live counts, one click to filter. A chip with nobody in it is hidden rather than shown as a zero. When a filter is on, every row says why it is in the list — a list of names with no reason is a list you have to take on trust.
  - The existing action bar works on the filtered set, so "everyone whose passport won't make it" is now something you can tag, task or start a sequence for in one go.
- [x] **3. Custom fields per agency** (1 Aug) — Attio's actual differentiator is a data model you shape yourself. Every agency has three or four things it records that no other agency does: a loyalty number, the wedding date, a corporate account code, which of the two offices looks after them. Without somewhere to put them the answer is a spreadsheet beside the CRM.
  - **`lib/custom-fields/schema.ts` (25 tests)** — six types (text, number, date, choose one, choose several, yes/no), validation, coercion and display.
  - **Definitions in a table, values in jsonb on the record.** Every screen that already loads a customer gets their fields for free: no join, no second query, no page rendering half a record while it waits.
  - **Unknown keys are dropped, never stored.** The moment a browser can put arbitrary json in that column, "what fields exist" stops being a question anyone can answer.
  - **A field's type never changes.** Turning text into a number would quietly reinterpret every value already recorded — "approx 3" becomes nothing and nobody is told. The API refuses it in those words rather than silently ignoring the attempt.
  - **Fields are retired, not deleted**, because deleting the definition orphans every value under it. A retired field comes off the form and its values stay on the record, labelled "no longer in use".
  - **A value whose option was removed still shows, marked.** Blanking data an agency typed because someone edited a dropdown is a loss nobody notices until they need it.
  - **Merged, not replaced**, on save: a form that only rendered the fields on screen cannot wipe a value it never showed.
  - Entity is `household` only, on purpose — it is the one record with a detail screen to put fields on. Adding trips or contacts is a one-line constraint change plus a column, and should happen when there is a screen for them.
